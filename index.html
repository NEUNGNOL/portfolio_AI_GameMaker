AI 리더십

AI와 사람의 역할을 나눔
  • 구현 초안, 로그 분석, 자료 생성은 AI. 문제 정의, 우선순위, 검증, 출시 결정은 스스로.
  • AI 제안을 그대로 쓰지 않고 대안을 받아 비용과 리스크를 바탕으로 선택.
  • AI가 준 코드가 콘솔을 초당 수백 줄로 채우는 것을 실행 중에 발견하고 조건을 걸어 고침.

지키는 규칙 다섯 가지

규칙이유실제로 막은 일
대안을 2~3개 받음첫 답만 받으면 AI의 기본값을 그대로 쓰게 됨. 비교해야 내 판단이 들어감.위젯 스크롤 목록안(코드 3배)을 피하고 반나절짜리 자동 조절안을 고름.
로그는 원문 그대로요약하면 단서가 사라짐. 깨진 경로 한 줄이 원인이었음.한글 사용자 경로 문제를 로그의 깨진 글자로 찾아냄.
코드는 직접 붙여 넣음읽으면서 옮기고, 이해하지 못한 코드는 남기지 않음.처음 쓰는 Flutter 구조를 2일 만에 파악하고 이후 수정 위치를 스스로 찾음.
가설은 테스트로 확정"아마 이거"로 고치면 재발함.알림 버그를 테스트 9종으로 확정한 뒤 한 번에 고침.
출시 조건에서 검증개발 모드에서만 돌리면 AI도 나도 놓치는 문제가 있음.출시 빌드에서만 나는 즉시 종료를 업로드 전에 발견함.

기능 요청"위젯에 일정이 최대 3개만 보인다. 크기를 늘리면 공간이 비고 줄이면 잘린다. 해당 이슈를 보안하여 수정하기 위한 방향 시안과 개발 명세서를 작성하여 전달해."

AI에게 정답이 아니라 내가 판단할 재료(명세, 대안, 가설)를 요청합니다.

    AI 제안을 그대로 받지 않은 결정

    위젯 표시 개수 문제

    A 높이에 맞춰 줄 수 자동 조절, B 위젯 안 스크롤 목록, C 크기 고정
    B가 가장 완성도 높지만 코드가 3배 이상이고 출시 빌드 오류 위험이 컸음. 테스트 마감 7일 전이라 A를 골랐고, B는 지표를 보고 정할 예정.

    '하는 중' 표시 방식

    반쯤 찬 원 아이콘 (색약과 테마 대응을 근거로 추천)
    테마 4종에 그대로 적용되는 텍스트 'Today · 하는 중'으로. 위젯은 제외해 파일 4개 수정으로 끝냄.

    전면광고 추가

    테마 변경 시 전면광고를 넣는 안 검토
    사용자당 빈도가 낮고 '쉬엄쉬엄' 콘셉트와 충돌함. 2~4주 Firebase 지표를 본 뒤 정하기로 보류함.

    "가끔 안 사라진다"를 조건별 테스트로 쪼갬

    테스터 제보는 "되돌리기 알림을 직접 내려야 한다. 근데 사라질 때도 있다"였습니다. 바로 고치지 않고 AI에게 가설과 테스트 케이스를 받아 제가 직접 실행하고 판정했습니다.

    정상문제테스트 불가
    ID분리한 조건수정 전수정 후
    TC-01, 02해결하거나 미루고 10초 대기계속 표시5초 뒤 사라짐
    TC-03A를 밀고 1초 뒤 B를 밂A만 밀려 사라짐B도 5초 뒤 사라짐
    TC-04, 05되돌리기 누름, 버튼 없는 알림 (대조군)정상정상 유지
    TC-06보관함에서 삭제계속 표시7초 뒤 사라짐
    TC-07, 08화면 이동, 앱 전환유지사라짐
    TC-09TalkBack 사용 중테스트 불가유지가 정상

    "가끔 사라진다"는 실제로 "다른 동작에 밀려서만 사라진다"였습니다. 대조군이 정상이라 원인을 버튼 있는 알림의 자동 종료 설정으로 좁혔고, 노출 시간은 복구 가능 여부로 나눴습니다(해결과 미루기 5초, 되돌릴 수 없는 삭제 7초). 이 표는 이후 업데이트마다 회귀 테스트로 다시 씁니다.

    피드백은 요청 그대로가 아니라 가장 싼 해법으로

    테스터 피드백검토한 안선택과 이유
    "주간 일정이 생기면 할 일이 1~2개만 보인다"화면 스크롤, 등록창 모달, 접기화면 전체 스크롤. '빨리 적고 넘기는' 흐름을 지키고 파일 1개만 고침.
    "빨래처럼 돌려놓고 기다리는 일을 표시하고 싶다"아이콘, 색상, 텍스트텍스트. 해결과 미루기 색과 겹치지 않고 모든 테마에 적용됨.

    필요한 순간에 배우고 바로 적용함

    Unity 개발자로서 Flutter와 Android는 처음이었습니다. AI에게 "유니티로 치면 무엇인지" 비유로 설명을 받아 개념을 빠르게 연결했습니다.

    • 1일차Flutter 위젯 구조, setState (MonoBehaviour와 Layout Group에 대응), Android SDK와 Gradle메인 화면, 스와이프, 등록창 완성. 한글 경로, NDK, 캐시 빌드 실패 3건 해결

    • 1주차ThemeExtension, 커스텀 폰트, Kotlin 홈 화면 위젯테마와 위젯 업데이트 배포
    • 2주차Firebase Analytics, GA4 측정기준과 퍼널이벤트 8종 설계와 구현, 핵심 이벤트와 퍼널 구성

    가장 크게 배운 순간: 출시 빌드에서만 꺼지는 앱

    개발 모드에서는 잘 돌던 앱이 출시 모드에서는 켜자마자 꺼졌습니다. 업로드 직전 점검에서 발견했습니다.

    범위 좁히기개발 모드와 출시 모드로 조건을 나눠 출시 빌드만의 문제임을 확인
    로그 해석크래시 로그 원문을 받아 원인 후보를 제시
    원인 확정코드 압축(R8)이 라이브러리 내부 클래스를 지운 것을 확인
    수정과 재검증예외 규칙을 추가하고 출시 모드에서 다시 실행
    • AI가 짠 코드든 내가 짠 코드든 실제 배포 조건에서 확인해야 함.
    • 업로드 전 출시 모드 실행을 릴리즈 체크리스트 필수 항목으로 고정함.
    • 위젯과 Firebase를 추가할 때도 같은 절차로 검증해 재발이 없었음.

    게임이 아니라 에디터에 붙는 도구임

    인터넷 밈 "슬플 때 기억하세요. C6 척추뼈는 매일 당신을 지지하고 있습니다"에서 출발했습니다. 그 목뼈는 개발자가 여덟 시간을 구부정하게 앉아 있는 동안에도 버티고 있으니, 화면 구석에서 대신 지쳐가게 만들었습니다.

    게임 빌드가 아니라 EditorWindow로 만들었기 때문에 일반적인 게임 코드가 통하지 않습니다. 이 두 가지가 이 프로젝트의 실제 난이도였습니다.

    에디터의 제약왜 막히는가해결
    게임 루프가 없음플레이 모드가 아니면 Update()도 Time.deltaTime도 돌지 않음EditorApplication.update에 콜백을 걸고 timeSinceStartup의 차분으로 델타를 직접 계산
    코드를 고치면 상태가 사라짐재컴파일 때마다 C# 도메인이 재생성되며 static 값과 이벤트 구독이 전부 초기화됨상태는 도메인 밖 SessionState에, 재구독은 [InitializeOnLoad]로

    고치기 전에 문제를 먼저 재현함

    타이머가 50초까지 쌓인 상태에서 스크립트를 저장하자 콘솔의 숫자가 0초부터 다시 시작했습니다. "코드를 고칠 때마다 리셋되는 작업 시간 추적 도구"는 도구로서 성립하지 않으므로, 원인을 확정하고 고쳤습니다.

    재현시간을 쌓아 둔 채 스크립트를 저장해 리셋되는 것을 눈으로 확인
    원인 해석도메인 리로드로 static과 구독이 함께 소실된다는 설명
    해결경과 시간·단계를 SessionState에 저장하고 리로드 직후 복원·재구독
    재검증같은 절차를 다시 실행해 숫자가 이어지는 것을 확인
    • "아마 이것 때문"으로 넘기지 않고 재현 → 원인 → 해결 → 재검증 순서를 지킴.

    적용해 보니 I키로 다시 열리지 않았음. 엔진 기본 UI가 닫을 때 쓰는 방식을 확인해 같은 방식(Enable 끄기)으로 맞춤.

    엔진이 이미 8초짜리 획득 팝업을 띄워 알림이 두 번 뜸. 커스텀 팝업을 지우고 엔진 기능에 맡김.

    문서에 없는 버그는 소거법으로 좁힘

    타이머 시작 함수가 호출되고 로그도 정상인데 타이머가 흐르지 않았습니다. 대입 직후에는 true였던 값이 다음 프레임에 false로 돌아가 있었고, 되돌리는 코드는 어디에도 없었습니다. 추측으로 고치지 않고 가설을 하나씩 지웠습니다.

    기각확정
    가설검증 방법결과
    다른 인스턴스에 쓰고 있음양쪽에서 엔티티 이름 출력동일 인스턴스
    다른 코드가 값을 끔정지 함수에 호출 로그호출 없음

    동기화(@Sync)가 덮어씀@Sync 제거 후 재현동일하게 재현
    프로퍼티 쓰기 자체가 안 됨OnUpdate에서 값 강제 누적정상 누적
    @ExecSpace 메서드에서 쓴 값만 사라짐위 다섯 결과의 소거확정
    재현호출 로그는 정상, 다음 프레임 값만 되돌아가는 조건을 고정
    가설 목록원인 후보 여섯 개와 각각을 확인할 로그 코드
    판정엔진에서 하나씩 실행해 다섯 개를 기각
    패턴화메서드는 요청 플래그만 세우고 실제 변경은 OnUpdate에서 처리
    • 이후 외부에서 호출되는 모든 메서드(팝업 열기, 대화창, 랭킹 갱신, 시즌 재조회)에 같은 패턴을 적용함.
    • 엔진 동작이 문서와 다를 때는 추측보다 소거가 빠르다는 것을 확인함.

    Server는 클라이언트를 막지 않음

    스테이지 입구 트리거가 실행될 때마다 타이머가 재시작되고 처치 수가 초기화됐습니다. 로그를 보니 같은 핸들러가 서버와 클라이언트에서 한 번씩, 총 두 번 실행되고 있었습니다.

    실행 공간 설정클라이언트에서 호출되면
    미지정클라이언트에서 실행
    Server서버로 보내 실행 (호출 자체는 일어남)
    ServerOnly무시

    충돌 이벤트는 서버와 클라이언트가 각자 감지하므로 트리거 계열 핸들러를 ServerOnly로 통일했습니다. 이미 잘 돌던 아이템 획득 코드는 처음부터 ServerOnly였습니다. 기존 코드가 왜 그렇게 쓰였는지 확인하지 않은 것이 원인이었고, 이후 새 코드를 쓰기 전에 비슷한 기존 코드부터 읽습니다.

    시즌 랭킹은 저장소 구조부터 나눔

    저장소키쓰는 곳
    유저 저장소역대 최고, 시즌별 최고학자버섯 대사, 내 기록 표시
    정렬 저장소시즌별 랭킹 (유저 ID → 점수)랭킹 팝업 1–7위, 왕좌 1–3위
    전역 저장소유저 ID → 닉네임접속하지 않은 유저 이름 표시

    정렬 저장소는 정수만 담을 수 있어 닉네임을 따로 저장하고, 점수를 저장하는 순간에 함께 기록했습니다. 순위 목록은 구분자 문자열로 직렬화해 클라이언트에 동기화했습니다. 시즌은 기준 시각부터의 경과 분을 시즌 길이와 휴식 길이로 나눠 계산하고, 휴식 기간에는 역대 기록만 갱신하고 랭킹에는 반영하지 않습니다.

    기획자가 혼자 할 수 있게 만듦

    데이터 테이블 행 입력, 인스펙터 연결, 태그 배치는 기획자가 맡을 수 있도록 구조를 짰습니다. 포자 상점의 가격과 아이콘, 어빌리티 효과 수치, 드롭 테이블은 모두 데이터 테이블에서 바뀝니다. 그리고 항목이 빠졌을 때 어떤 증상이 나타나는지까지 적은 체크리스트를 따로 만들었습니다. 예를 들어 인벤토리 아이템 정의 행이 없으면 구매는 되지만 아이콘이 비고 사용이 안 됩니다.

    AI가 짠 코드를 엔진 지식으로 바로잡음

    서브 프로그래머가 AI로 작성한 몬스터 경계 표시(머리 위 느낌표) 코드를 리뷰했습니다. 모든 몬스터 모델에 느낌표 자식 엔티티를 미리 붙여 두고, 상황에 따라 스프라이트를 켜고 끄는 방식이었습니다. 동작은 했지만 엔진 구조를 고려하지 않은 하드코딩 방식이라, 몬스터가 늘어날수록 모델마다 수작업이 쌓이고 하나라도 빠지면 에러 없이 조용히 안 보이는 구조였습니다.

    비교기존: 자식 스프라이트 켜고 끄기변경: 이펙트 재생
    몬스터 추가 시모델마다 자식 엔티티를 붙이고 스프라이트, 정렬, 위치를 설정추가 작업 없음
    설정 누락 시에러 없이 표시되지 않음모델에 의존하지 않아 누락될 곳이 없음
    코드자식 탐색, 유효성 검사, 렌더러 속성 직접 세팅이펙트 재생 호출 한 줄

    MSW에는 엔티티 위치에 이펙트를 재생하는 API가 있어, 모델을 건드리지 않고 호출 한 줄로 같은 연출을 낼 수 있습니다. 이 방식을 제안하면서 프로젝트에서 이미 검증된 호출을 인자까지 채워 넘겨, 서브 프로그래머가 바로 교체할 수 있게 했습니다. 몬스터 AI 통합 때도 하드코딩된 애니메이션 재생을 엔진 표준 컴포넌트로 바꾸고, 미선언 필드 접근으로 생기는 크래시를 정리했습니다.

    • AI가 준 코드는 돌아가는지보다 이 엔진에 맞는 방식인지를 먼저 봄. 그 판단은 엔진 도메인 지식에서 나옴.
    • 베타 서비스 중에는 스펙을 확인할 수 없는 조명 컴포넌트 대신 검증된 API만 쓰는 스프라이트 방식으로 시야 제한을 만듦. 새 기능보다 라이브 안정성을 먼저 둠.
    • 실제 유저가 있는 환경에서는 "내 컴퓨터에서 된다"가 기준이 아님. 팀 QA 리스트를 받아 이슈 단위로 대응함.
